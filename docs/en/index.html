How it works

Four steps, always in the same order

The software suggests, the human confirms, the engine decides.

  1. IngestPaste an email or an incident report. A parser makes suggestions, nothing more.
  2. ReviewEvery legal question is confirmed with a click, with the provision and its reasoning next to it.
  3. DecideThe engine evaluates the confirmed facts and approves the action, requires a review, or blocks it.
  4. ExecuteOnly now is the document produced. Every step lands in a hash-chained log.

Possible decisions: PERMITTEDMANUAL_REVIEWBLOCKED

Rulebooks

Two rulebooks, one engine

The domain knowledge lives in rulebooks that are plain data. The engine knows nothing about the GDPR; it only executes what a rulebook describes.

  • dsar-gdpr-de

    Data subject requests

    Access (Art. 15), erasure (Art. 17) and extension of the deadline (Art. 12(3) GDPR). The result is the matching reply letter, from a negative response to a full disclosure with a copy of the data.

  • breach-gdpr-de

    Data breaches

    Notification to the supervisory authority (Art. 33) and communication to data subjects (Art. 34 GDPR). The result is a draft notification, the communication to data subjects and an internal record.

  • uri.rulebook/v1

    Your own rulebooks

    The format is documented. Your own rulebooks can be imported as JSON; they ship with their test cases and are only activated if all of them pass. Read the specification (German)

Also included: a deadline calculator with public holidays for all 16 German states, and a view that shows every decision as machine-readable JSON.

Why this way

Six deliberate design decisions

They explain why the tool behaves differently from a chatbot or a web form.

Rules are data, not code

Anyone who wants to check what the tool decides should not have to read program code. Each rule is an entry with a question, a legal source and an effect. The principle is borrowed from Open Policy Agent: the decision is separate from the place that enforces it. The second rulebook was added without changing a single line of the engine.

No AI makes the decision

With legal questions the same input must always lead to the same result, and you must be able to see why. That is why the engine is deterministic. The parser only reads the text aloud; something becomes a fact only through a click.

No silent assumptions

As long as a question is open, everything stays locked. If you change an earlier answer, the answers that depend on it are deleted and must be confirmed again. That costs a few clicks and prevents a letter from resting on an assumption nobody made.

The document comes last

A letter is not produced on the side but only after the engine approves it. For delicate outcomes, such as a refusal or a late notification, it additionally requires sign-off by a named person. That sign-off applies to exactly this set of facts.

Everything stays on your machine

Data subject requests and incident reports contain personal data. So there is no server, no account and no scripts loaded from elsewhere, just one file you can also open offline.

A log that states its limits

Each step is chained to the previous one with SHA-256, so later changes stand out. This supports accountability. It is not a guarantee against deliberate tampering in the browser, and the tool says so.

Limits

What it is not

A legal tool should be honest about where it stops.

  • Not legal advice. The tool is a workflow assistant. The rulebooks have not yet been reviewed by a data protection lawyer or officer.
  • Sources in progress. The short excerpts of statutory text have not yet been checked word for word against the originals; two citations among the case examples are flagged as unverified in the tool.
  • Risk values are set, not derived. The factors and thresholds are reasoned assumptions.
  • Deadlines are guidance values. Whether the German Civil Code or Regulation 1182/71 applies is disputed in detail.
  • Cases are not saved. The session is gone after a reload; export what you need.
  • German only for now. The application and the rulebooks are in German; an English interface is planned.
Contribute

Try it and get involved

The live version is the quickest way in. If you want to read or change the code:

git clone https://github.com/ECMBenjamin/dsar-regel-engine.git
cd dsar-regel-engine
npm install   # only needed for the tests
npm test      # builds the file and checks every answer path
  • Lawyer or data protection officer? A critical look at the rules and text modules helps most. Test cases can be written without programming; the specification explains how.
  • Developer? Writing your own rulebook is the best way in. Please report bugs and ideas as an issue.
  • Planned next: verified sources per rule, signed exports, local storage of cases, and an interface that lets AI agents query the engine before they act.
About

The DSAR Rules Engine is a project by Benjamin Thyssen. It is the first version of a larger idea: an infrastructure in which rules exist as versioned data, an engine evaluates them traceably, and only its decision releases an action, whether a human or an AI agent wants to act.
