Regeln entscheiden. Aktionen setzen durch.

Die DSAR Regel-Engine führt Schritt für Schritt durch DSGVO-Betroffenenanfragen und Datenpannen. Das Antwortschreiben oder die Meldung entsteht erst, wenn die Engine die Aktion freigibt. Alles läuft in einer einzigen HTML-Datei in Ihrem Browser; es werden keine Daten übertragen.

Was das Werkzeug macht

Jeder Vorgang durchläuft dieselben vier Schritte. Die Software schlägt vor, der Mensch bestätigt, die Engine entscheidet.

  1. EinlesenE-Mail oder Vorfallbericht einfügen. Ein Parser macht Vorschläge, mehr nicht.
  2. PrüfenJede rechtliche Frage wird einzeln per Klick bestätigt, mit Norm und Begründung daneben.
  3. EntscheidenDie Engine wertet die bestätigten Fakten aus und gibt die Aktion frei, verlangt eine Prüfung oder blockiert.
  4. AusführenErst jetzt entsteht das Dokument. Jeder Schritt landet in einem verketteten Protokoll.

Mögliche Entscheidungen: PERMITTED MANUAL_REVIEW BLOCKED

Zwei Regelwerke, eine Engine

Das Fachliche steckt in Regelwerken, die als reine Daten vorliegen. Die Engine kennt keine DSGVO; sie führt nur aus, was ein Regelwerk beschreibt.

dsar-gdpr-de

Betroffenenanfragen

Auskunft (Art. 15), Löschung (Art. 17) und Fristverlängerung (Art. 12 Abs. 3 DSGVO). Ergebnis ist das passende Antwortschreiben, von der Negativauskunft bis zur Vollauskunft mit Datenkopie.

breach-gdpr-de

Datenpannen

Meldung an die Aufsichtsbehörde (Art. 33) und Benachrichtigung der Betroffenen (Art. 34 DSGVO). Ergebnis sind Meldungsentwurf, Benachrichtigung und interner Vermerk.

Eigene Regelwerke

Das Format ist dokumentiert. Eigene Regelwerke lassen sich als JSON importieren; sie bringen ihre Testfälle mit und werden nur aktiviert, wenn alle bestehen.

Zur Spezifikation

Dazu kommen ein Fristenrechner mit Feiertagen aller 16 Bundesländer und eine Ansicht, die jede Entscheidung als maschinenlesbares JSON zeigt.

Warum ich es so gebaut habe

Hinter dem Werkzeug stehen ein paar Entscheidungen, die ich bewusst getroffen habe. Sie erklären, warum es sich anders verhält als ein Chatbot oder ein Formular.

Regeln sind Daten, nicht Code

Wer prüfen will, was das Werkzeug entscheidet, soll keinen Programmcode lesen müssen. Jede Regel steht als Eintrag mit Frage, Rechtsquelle und Wirkung in einem Regelwerk. Die Engine führt es nur aus. Das Prinzip ist vom Open Policy Agent abgeschaut: Die Entscheidung ist von der Stelle getrennt, die sie durchsetzt. Ein neues Rechtsgebiet ist damit ein neues Regelwerk und kein neues Programm; das zweite Regelwerk kam hinzu, ohne eine Zeile der Engine zu ändern.

Keine KI trifft die Entscheidung

Bei Rechtsfragen muss dieselbe Eingabe immer zum selben Ergebnis führen, und man muss nachvollziehen können, warum. Deshalb ist die Engine deterministisch. Der Parser liest den Text nur vor und macht Vorschläge; zu einem Fakt wird etwas erst durch einen Klick.

Keine stillen Annahmen

Solange eine Frage offen ist, bleibt alles gesperrt. Ändert man eine frühere Antwort, werden die davon abhängigen Antworten gelöscht und müssen neu bestätigt werden. Das kostet ein paar Klicks und verhindert, dass ein Schreiben auf einer Annahme beruht, die niemand getroffen hat.

Das Dokument ist der letzte Schritt

Ein Schreiben entsteht nicht nebenbei, sondern erst nach Freigabe durch die Engine. Bei heiklen Ergebnissen, etwa einer Ablehnung oder einer verspäteten Meldung, verlangt sie zusätzlich die Freigabe durch einen Menschen mit Namen. Diese gilt nur für genau diese Faktenlage.

Alles bleibt auf dem eigenen Rechner

Betroffenenanfragen und Vorfallberichte enthalten personenbezogene Daten. Ein Werkzeug dafür sollte diese Daten nirgendwohin schicken. Deshalb gibt es keinen Server, kein Konto und keine nachgeladenen Skripte, sondern eine Datei, die man auch ohne Internet öffnen kann.

Ein Protokoll, das seine Grenzen nennt

Jeder Schritt wird per SHA-256 mit dem vorherigen verkettet; nachträgliche Änderungen fallen auf. Das dient der Rechenschaftspflicht. Es ist keine Garantie gegen gezielte Manipulation im Browser, und das steht auch so im Werkzeug.

Was es nicht ist

Ein Rechtswerkzeug sollte offen sagen, wo es aufhört.

  • Keine Rechtsberatung. Das Werkzeug ist ein Workflow-Assistent. Die Regelwerke sind noch nicht von einer Fachanwältin oder einem Datenschutzbeauftragten abgenommen.
  • Quellen in Arbeit. Die kurzen Normtext-Auszüge sind noch nicht wörtlich gegen die Originale abgeglichen; zwei Fundstellen der Fallbeispiele sind im Werkzeug als ungeprüft markiert.
  • Risikowerte sind gesetzt. Die Faktoren und Schwellen sind begründete Annahmen, keine hergeleiteten Größen.
  • Fristen sind Orientierungswerte. Ob BGB oder VO 1182/71 gilt, ist im Detail umstritten.
  • Vorgänge werden nicht gespeichert. Nach dem Neuladen ist die Sitzung weg; exportieren Sie, was Sie brauchen.

Ausprobieren und mitmachen

Am schnellsten geht es über die Live-Version. Wer den Code lesen oder ändern will:

git clone https://github.com/ECMBenjamin/dsar-regel-engine.git
cd dsar-regel-engine
npm install   # nur für die Tests
npm test      # baut die Datei und prüft jeden Antwortpfad
  • Sie sind Juristin oder Datenschutzbeauftragter? Am meisten hilft ein kritischer Blick auf die Regeln und Textbausteine. Testfälle lassen sich ohne Programmierkenntnisse schreiben; die Spezifikation erklärt, wie.
  • Sie entwickeln? Ein eigenes Regelwerk ist der beste Einstieg. Fehler und Ideen bitte als Issue.
  • Als Nächstes geplant: geprüfte Quellen je Regel, signierte Exporte, lokale Ablage von Vorgängen und eine Schnittstelle, über die KI-Agenten die Engine abfragen, bevor sie handeln.

Über das Projekt

Die DSAR Regel-Engine ist ein Projekt von Benjamin Thyssen. Sie ist die erste Fassung einer größeren Idee: einer Infrastruktur, in der Regeln versioniert als Daten vorliegen, eine Engine sie nachvollziehbar auswertet und erst ihre Entscheidung eine Handlung freigibt, egal ob ein Mensch oder ein KI-Agent handeln will.
